# Research MCP security and status

## Stage B behavior

`POST /api/workflows` applies a separate in-memory limiter (20 requests per 15 minutes per client IP by default), then the existing Supabase Bearer-token middleware, then request validation and Research handling. Invalid or missing credentials cannot reach Research execution. Requests stay on this route and never enter `/api/chat`, `/api/agent`, or the Security Investigation tool registry. Code, Build, and Structure Learn remain unimplemented.

Research input is intended only for general questions answerable from public sources. Do not include credentials, personal data, confidential or internal information, security targets under investigation, incident details, findings, logs, or prior investigation context. The API accepts only the current question; it does not accept conversation history. It validates the common versioned workflow envelope and permits only `maxResults` (1–5), `containsPersonalData`, and `containsConfidentialData`. Questions are capped at 1,000 characters / 2 KiB UTF-8.

The server-side privacy screen rejects recognizable credentials/tokens/private-key markers, email-like and defanged email forms, SSNs, common phone numbers, URLs, bare/defanged hostnames, IPv4/IPv6 literals, likely confidential/security language, and target-oriented investigation phrasing. Rejected values are not logged, echoed, or passed to the manager. The screen is a heuristic risk reduction only: it cannot establish whether information is public, and it will miss paraphrases, novel secret formats, identifiers embedded in prose, and sensitive context that is not stated. It can also reject harmless questions that include a hostname, phone-like number, or security wording. The user-supplied privacy booleans are additional declarations, not proof that other input is safe. The hard offline gate remains the actual protection against external Research calls in this phase.

The default Tavily MCP manager is hard-disabled by `OFFLINE_ONLY_STAGE`. Setting environment variables or passing `enabled: true` cannot enable the real default Tavily client in this phase; the manager rejects that path before client creation. Tests may inject a local/mock client factory, but the active Express route always uses the disabled default manager. A future live path would require a deliberate code change plus `RESEARCH_MCP_ENABLED=true`, `RESEARCH_MCP_LIVE_CALLS_ALLOWED=true`, and a Node 20+ runtime check. No live connection or provider call is made by this implementation.

### Backend-enforced confirmation (Stage F)

Research preparation uses authenticated `POST /api/workflows/research/prepare` with a query and the existing bounded Research options. The server screens the query before creating a confirmation; rejected input is not logged, echoed, or sent to a provider. A successful preparation returns the exact trimmed query, fixed provider name (`Tavily`), selected result count, a random confirmation identifier, and an expiry timestamp. This is a preview only: no provider request occurs during preparation. The user-facing flow must show the exact query and provider, explain that it will be sent externally if live Research is later enabled, and require an explicit confirmation action.

`POST /api/workflows/research/confirm` requires the authenticated user, confirmation identifier, exact previewed query, provider name, and `confirmed: true`. The server compares all fields with its stored record and consumes the record synchronously before starting the Research handler. Missing, malformed, changed, expired, cross-user, reused, or concurrent replay attempts fail without starting Research. A confirmation identifier or boolean by itself is not sufficient. Confirmation requests do not accept a user ID from the client. The normal `/api/workflows` Research request no longer invokes the handler directly and returns `RESEARCH_CONFIRMATION_REQUIRED`.

Pending confirmations are held in a bounded process-local map (up to 1,000 pending records) with a five-minute default lifetime. Records contain only the verified Supabase user ID, the exact normalized query, fixed provider, bounded Research options, and expiry. They are not persisted and are not logged. Process restarts invalidate pending confirmations; requests routed to another application instance cannot redeem a record created elsewhere. This fails closed but means the confirmation flow is not reliable across instances. Before live provider use, either use a shared short-lived store with atomic consume semantics or ensure single-instance routing and accept the restart/instance limitations; an authenticated-user quota and abuse control remain separate requirements.

The Stage G frontend adds a separate Public Research mode. It uses the existing authenticated request helper, sends no chat history, keeps the confirmation ID only in component memory, and displays the server-returned query/provider/result count/expiry before confirmation. Editing the query or result count invalidates the preview; cancel only clears local state and makes no confirm request. Requests use a Bearer Authorization header, JSON content type, `credentials: omit`, and redirect rejection; they do not rely on ambient cookies for authentication. The browser UI reports authentication, expiry/reuse, network, and provider-disabled outcomes without exposing exception details. This frontend was verified by API/controller tests and a production build; no browser-driven DOM automation is configured in the client project.

The hard `OFFLINE_ONLY_STAGE = true` gate remains enabled. Even a valid, consumed confirmation reaches the existing default manager, which returns provider-disabled before client initialization or network access. This stage establishes the backend confirmation boundary; it does not enable live Tavily calls or prove that the frontend presents the preview correctly. The privacy screen remains heuristic and cannot guarantee detection of all personal or confidential data.

### Rate limiting and proxy assumptions

The limiter is process-local and in-memory. Its allowance resets on process restart, is not shared between instances, and is keyed by Express's `req.ip`; it is not a per-user quota or durable provider-cost control. The app configures `trust proxy` to exactly one hop. Source code establishes that setting, but cannot establish Render's actual proxy chain, whether the origin is directly reachable, or whether forwarded client-address headers are rewritten at the edge. Confirm those properties in the Render dashboard/network configuration before relying on client-IP limits. Before provider use, use authenticated-user keying with an IP abuse guard and a shared store if multiple instances or durable limits are required. No shared service is added here.

The fixed provider endpoint is `https://mcp.tavily.com/mcp/`; the server reads `TAVILY_API_KEY` and places it in the Authorization header, never in a URL or response. The selected official client package is `@modelcontextprotocol/client` 2.0.0, imported through the documented `@modelcontextprotocol/client` package entry. It exposes `Client` and `StreamableHTTPClientTransport`, supports CommonJS exports, and requires Node `>=20`. The repository engine declaration remains `>=18`; runtime-incompatible environments are unavailable for MCP.

The connector uses only the `tavily_search` tool name found in Tavily's current public source, and still checks the discovered server inventory and input schema before invoking it. The known provider tool inventory is checked against a fixed set; unknown tools or schema drift fail closed. Arguments are constructed server-side from validated question/options, with basic search depth, general topic, and at most five results. There is one tool invocation per Research operation, a two-operation concurrency ceiling, a 10-second timeout, no retries/reconnection, an overall MCP HTTP response cap of 128 KiB, and a normalized-result cap of 64 KiB. The fetch wrapper pins the endpoint origin/path, rejects query/fragment destinations and redirects, and uses the shared streamed-byte limiter, which counts bytes before passing each chunk onward and cancels/releases the reader on overflow or abort. A chunk has already been materialized by the upstream stream before the limiter can count it; the configured total-byte cap is not a guarantee against allocation of one unusually large chunk. Provider results are parsed and normalized; only actual IDs/titles/timestamps are preserved, URLs must be HTTP(S) and must not contain credentials or literal private/local destinations, and unsupported records are discarded or fail closed. Source URLs are not independently resolved, fetched, or verified.

## Status semantics

| Status | Meaning |
| --- | --- |
| `unavailable` | Provider access is disabled, not configured, incompatible, or unreachable; no successful research is claimed. |
| `timeout` | An MCP request exceeded its bounded timeout. |
| `empty` | A valid provider response contained no source records. |
| `success` | Valid source records were normalized from the MCP result. This is provider evidence, not independent verification or generated synthesis. |
| `partial` | At least one valid source was retained while one or more malformed or unsafe records were discarded. |
| `error` | Request/privacy validation or provider-output validation failed. |

Every response uses the workflow version-1 envelope. `metadata.executionStatus` is `not_started` while the provider remains disabled, `failed` after a typed provider-operation failure, and `completed` only after a provider result was received and normalized. The current disabled response is HTTP 503 with `status: "unavailable"`, `error.code: "RESEARCH_PROVIDER_DISABLED"`, empty sources, and `executionStatus: "not_started"`.

## Tavily data handling and live-use gate

Tavily's public privacy policy says it collects query data to retrieve web content, may use portions to improve future responses unless a contract says otherwise, and may share queries with third-party search-index providers in limited circumstances. Its retention clause uses a service/operational-need standard rather than a query-specific duration. Its terms separately state that customer input submitted to its AI functionality may be used by Tavily and third-party AI providers for model training and improvement. The public materials reviewed do not establish whether an MCP `tavily_search` call is covered by that AI-functionality clause, nor provide a precise retention duration for MCP search query logs. See [Tavily Privacy Policy](https://www.tavily.com/privacy) and [Tavily Terms](https://www.tavily.com/terms).

Do not send confidential or personal data. Before any separate approval to enable live Research, confirm the Render service root directory, build/start commands, production Node version, and which package manifest/lockfile are used. The MCP SDK is declared in the repository-root manifest/lockfile; the separate `server/package.json` and `server/package-lock.json` do not currently declare it. Obtain a provider data-handling decision for MCP search query retention, provider logs, training/improvement, and third-party processing. Review privacy-screen limitations and establish user-facing notice/consent as required. Confirm the Render reverse-proxy hop count and that the origin cannot be reached in a way that bypasses trusted-header rewriting. For multiple instances or durable provider-cost limits, approve a shared rate-limit store or authenticated-user quota before activation. Add offline and deployment verification; do not treat public source code or local mocks as proof of remote endpoint compatibility or production settings.
