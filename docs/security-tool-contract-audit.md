# Lakewest AI — Security Tool Contract and Data-Handling Audit

**Scope:** canonical active tool registry and execution path in `server/agent-server.js`. This is a source inspection only; no provider requests or remote scans were run. No application or tool behavior was changed for this audit.

**Snapshot note:** this report records the Stage 2H.7 pre-remediation state. Stage 2H.8 changed the Observatory metadata to `write`, added the `security_remote_scan` capability requirement, and marked approval required. Active execution remains disabled until a consent/approval workflow is implemented. See the updated current contract in `docs/tool-contract.md`.

## Executive summary

The active registry contains 15 implementation-backed Security tool entries plus five compatibility aliases. Each is registered with `riskLevel: "read"`, `requiresApproval: false`, and no `requiredCapability`. The active `/api/agent` route requires a verified Supabase bearer token, but that is route authentication rather than per-tool authorization: every authenticated caller can reach the registered read-risk tools, and no current tool consumes the server allowlist capability grants. `ToolPolicy` and `AgentLoop` enforce the declared metadata before execution, but the metadata does not express all actual data handling or side effects.

The notable contract mismatch is `mozilla_observatory_scan`: its implementation POSTs a scan request to the external Observatory API. This can trigger remote scanning activity and should not be described as a pure lookup. A POST alone is not evidence of a side effect: URLhaus and ThreatFox POST query requests to fixed provider endpoints, and their code performs lookup operations.

No registered tool fetches an arbitrary user-provided URL from the Lakewest server. Tool requests go to fixed provider endpoints, and the Phishing.Database feed is fetched from a source-controlled fixed URL. Consequently, submitted indicator URLs are data sent to selected providers, not Lakewest HTTP destinations. Provider retention and deployed egress/proxy behavior were not verified; the fixed feed host still relies on runtime DNS and network routing.

## Active execution and enforcement path

1. `server/agent-server.js` constructs tools and registers them in `toolRegistry`; `ToolRegistry.register()` normalizes their risk, approval, and capability fields.
2. `/api/agent` is behind `requireAuthenticatedSupabaseUser`. It passes a context from `getRequestCapabilityContext(req)` into `AgentOrchestrator.run()`.
3. Provider-requested calls and controller-required calls converge on `AgentLoop._executeTool()`.
4. `_executeTool()` rejects unknown/internal aliases or investigation-target mismatches, runs `ToolValidator.validate()`, then `ToolPolicy.check()`. It calls `tool.execute()` only after these checks and the controller read-risk check. Execution results/errors are normalized into evidence and returned to the agent loop.
5. `AgentAuditLogger` redacts fields whose names resemble credentials and logs lifecycle/policy metadata. It does not log full tool outputs in the reviewed call path. Tool results remain in agent evidence/model context; `/api/agent` returns the synthesized `safeReply` and investigation metadata rather than raw tool evidence. The PDF/report path consumes investigation data separately.

`ToolValidator` performs shallow schema checks. Individual tools also validate targets, but those checks vary in strictness. Timeouts are generally 8 seconds per provider attempt (10 seconds at the agent tool boundary); Phishing.Database uses a 10-second feed timeout. `fetchWithRetry()` makes at most one retry by default and aborts each request attempt. The outer `AgentLoop` timeout race does not itself cancel arbitrary promises; the current provider fetch implementations generally have their own abort timeout.

## Findings

### High

**H1 — Remote scan is authorized as ordinary read. Confirmed.** `createMozillaObservatoryTool()` posts a host to a scan endpoint and accepts successful scan IDs/results, while the registration declares `readOnly:true`, `riskLevel:"read"`, `requiresApproval:false`, and no `requiredCapability`. `ToolPolicy` therefore allows it for the `/api/agent` caller as an ordinary read operation; `AgentLoop` invokes it after validation/policy. This is an external action, not merely an HTTP-method concern. Minimum proposed change: classify it as `write` (which the active default policy denies) and keep it unavailable until a separate explicit remote-scan capability and an actual approval/consent control are designed. Do not treat `requiresApproval:true` alone as a workflow; current `ToolPolicy` denies approval-required tools outright.

### Medium

**M1 — No registered tool has granular capability authorization. Confirmed.** Registry inspection shows every registered Security tool/alias has no `requiredCapability`; the resolver’s allowlist therefore gates none of them. Supabase authentication protects `/api/agent`, but any authenticated principal can reach these tools. Recommended: assign explicit capabilities per tool after product policy and data-handling review; retain public `/api/chat` behavior separately.

**M2 — Sensitive values are sent to external providers. Confirmed behavior; external retention/logging is unverified.** HIBP requires the exact email in its lookup path. Stage 2H.17 keeps that provider request unchanged and removes redundant copies from successful/no-match tool findings and generated evidence. The address remains in the user request and agent scope/tool call sent to the configured AI provider, and in the canonical investigation target and source attribution needed to identify the subject. The PDF uses the investigation target as its displayed target and breach findings no longer repeat the address. Google Web Risk, Shodan, IPinfo, and ViewDNS place API credentials in outbound query strings. URL-capable providers transmit full URL indicators, which can include user-specific path/query data. Provider, AI-provider, hosting, proxy, and monitoring retention is outside what this repository can verify.

**M3 — Personal data can appear in generic audit values. Partially mitigated in application logs.** `AgentAuditLogger` redacts email-shaped values in strings, including target/message fields. AgentLoop also stores HIBP's duplicate email input as `[REDACTED_EMAIL]` in its evidence and executed-call records; provider execution and query matching still use the exact input. The source remains tagged with its investigation target under the existing attribution contract. This does not control process memory snapshots, crash dumps, external telemetry, or third-party logs.

### Stage 2H.17 — HIBP email handling

The exact submitted address is required for HIBP breach matching and remains in the request path (after existing trim/validation and URL encoding). HIBP findings and generated evidence no longer contain a separate `email` field. AgentLoop masks redundant stored-input copies in successful and failed evidence/executed-call records using the existing audit sanitizer; tool execution, target resolution, and the HIBP request keep the original value. The canonical investigation target and HIBP source retain attribution; `targetIdentity.normalized` remains for existing confidence checks, while the duplicate `targetIdentity.raw` is omitted for email targets. The report displays the canonical target with breach facts and uses a generic `email-investigation` download filename. The active `/api/agent` response returns synthesized content and investigation metadata, not raw tool evidence; no application database or persistent HIBP result store was found in this path. The model provider receives the user message and authoritative target/tool context, so the full address remains part of that provider request and generated text could repeat it. HIBP, AI-provider, hosting, proxy, and monitoring retention cannot be established or controlled from this source review.

**M4 — Censys provider error-detail disclosure. Remediated in Stage 2H.24 for the reviewed non-success HTTP path.** The adapter now returns the fixed public message `Censys request failed`, preserving `statusForHttp()` classification. Its direct `console.warn()` emits only a validated HTTP status and a fixed internal category; provider body fields, raw response content, request data, and authentication headers are not copied. The serialized diagnostic object is capped at 128 bytes, with a test asserting the captured log arguments remain within 256 bytes. Synthetic tests include fake API-key and bearer-token strings, an email address, and a long string and verify none reach logs or results. This remediation is specific to Censys non-success HTTP handling; it does not establish that other provider adapters’ direct console logging is sanitized.

**M5 — Provider response bodies require a byte ceiling. Remediated for reviewed fetch-based security-tool and AI-provider adapters in Stages 2H.16, 2H.21, and 2H.23.** The shared reader enforces a 2 MiB default limit (`PROVIDER_MAX_RESPONSE_BYTES` can lower or raise it to at most 10 MiB) while counting streamed bytes before decoding or JSON parsing. Missing or malformed `content-length` is ignored; streamed byte count remains authoritative. Oversize bodies are cancelled and raise a fixed `response_too_large` error without body, URL, or credential data; the shared security-tool request helper does not retry oversize responses. Both AI provider base classes keep the abort timeout active through buffered body consumption, and legacy raw-response modes retain the timeout through bounded stream consumption/cancellation. AI `response_too_large` errors now stop fallback; other transient provider failures retain existing fallback behavior. Phishing.Database feed fetching has its separate 5 MiB streaming limit. Coverage is limited to adapters that use these shared paths; direct or SDK-managed paths added later require review. The cap does not bound normalized result counts when a valid response fits under it.

### Low

**L1 — Input validation has uneven rigor. Confirmed.** `ToolValidator` is intentionally shallow and does not recursively validate JSON Schema constraints such as `minProperties`; provider-specific checks fill some gaps. For example, SecurityTrails accepts IP-shaped characters without `net.isIP`, URLScan accepts a broad IP-character pattern, and Mozilla’s `hostFor()` parses a hostname without restricting the input URL protocol. These do not redirect Lakewest’s HTTP request away from the fixed provider host, but can produce malformed submissions or unintended remote scan targets. Recommendation: use shared strict validators for IP/domain/URL and enforce mutually exclusive target fields where intended.

**L2 — Historical feed destination was environment-configurable. Remediated in Stage 2H.11; residual egress/DNS controls remain unverified.** Earlier code passed `PHISHING_DATABASE_FEED_URL` to the feed tool and used default Fetch redirect behavior. Current code does not read that environment variable: it validates and fetches the exact source-controlled HTTPS feed URL, sets `redirect: "error"`, applies a default 10s abort timeout, and reads at most 5 MiB before parsing. This removes request/deployment configuration and redirect destinations from the current feed path. It does not pin the fixed host's DNS answer or constrain the server's network route.

### Informational

**I1 — Several POST requests remain lookup-only. Confirmed.** URLhaus and ThreatFox send lookup/search query bodies to fixed provider endpoints; PhishTank also submits a lookup form but is not registered. Their method alone does not justify reclassifying them as write operations. VirusTotal URL lookup uses GET and does not submit a scan. URLScan’s registered tool searches historical records and does not invoke its scan-submission endpoint.

**I2 — All registered tools currently use the same risk/approval metadata. Confirmed.** Every entry is read/no approval/no capability; aliases copy their source tool metadata. `ToolRegistry.getDefinitions()` exposes the required capability field to providers but not risk or approval fields. Enforcement still occurs server-side in `AgentLoop`; provider-visible definitions are not the enforcement boundary.

## Confirmed issues vs. unverified concerns

**Confirmed by repository code (historical and current findings):** The former `PHISHING_DATABASE_FEED_URL` configuration plus default redirect behavior was a historical server-side SSRF concern, now mitigated in application code as described in Stage 2H.11/2H.18. Current source review found no fetch destination derived from a user-submitted indicator. Remaining confirmed repository findings include Observatory remote scan behavior and metadata concerns, sensitive values sent to providers, provider credentials in query strings, Censys provider error detail handling, and the unregistered PhishTank implementation. Stages 2H.16 and 2H.21 bound reviewed security-tool and AI-provider response bodies, respectively.

**Not established here:** runtime DNS answers or DNS integrity for the fixed feed host; production egress firewall/routing restrictions; proxy configuration, proxy redirects or TLS interception; actual deployed server environment and whether an obsolete unused `PHISHING_DATABASE_FEED_URL` variable remains; provider retention periods and provider-side logging; production reverse-proxy/APM redaction; and live provider credential scopes. No claim is made that these deployment concerns are exploitable.

## Prioritized minimal remediation plan

1. Disable or reclassify `mozilla_observatory_scan` as a write/remote-scan operation and require a purpose-built explicit authorization plus consent/approval flow before enabling it. Keep current functionality unchanged until that design is implemented.
2. Define per-tool capability grants and data classifications; add explicit `requiredCapability` metadata for tools that transmit personal/sensitive indicators or initiate external actions. Do not grant every capability to every authenticated user.
3. Remove credential query parameters where the provider supports headers; redact query strings in outbound transport diagnostics and ensure deployment logs do likewise.
4. Establish HIBP/email handling rules: explicit user intent, minimum data sent, no raw email in audit events, and documented retention/provider disclosure. Add field-aware redaction for email and sensitive URL components.
5. Maintain the shared response-byte limits and separately bound normalized records/error details. Replace Censys error-body reflection with allowlisted safe diagnostics.
6. Consolidate strict IP/domain/URL validation at each execution boundary. Keep the feed URL source-controlled and redirects disabled; add deployment egress/DNS restrictions where required by the hosting threat model.
7. Add offline tests for remote side-effect classification, PII/key redaction, URL forwarding rules, provider response-size limits, and malformed target rejection before implementing each remediation.

## Documentation mismatches

- `docs/tool-contract.md` says the registered HIBP ID is `hibp_email_lookup`; active registration is `hibp_lookup`.
- The contract document describes registered tools collectively as read-only but does not disclose that Mozilla Observatory initiates a remote scan. That implementation/metadata mismatch is detailed above.
- Tool-contract documentation describes external network and sensitive-data fields as future metadata; those fields remain unenforced in `ToolRegistry` today. In particular, HIBP’s email handling and Mozilla’s remote scan are not represented by dedicated contract metadata.
- PhishTank may be mistaken for an available tool because its implementation exists; it is not registered in the active backend.

## Verification and limits

This audit performed source inspection only. No tools were executed against providers, no remote scans were requested, and no deployment configuration was queried for secret values. Verification commands are reported in the task completion summary; this document itself does not establish production deployment behavior.

## Stage 2H.8 disposition

`mozilla_observatory_scan` now declares `riskLevel: "write"`, `requiredCapability: "security_remote_scan"`, and `requiresApproval: true`. The active policy continues to allow only `read`, and `ToolPolicy` denies approval-required tools because no approval workflow exists. The scan therefore remains disabled before the provider call, including for authenticated users and users with a server-side capability grant. No Mozilla alias is registered. A future enablement requires a trustworthy consent/approval flow plus an explicit server-side grant; login or request-body claims are insufficient. Other Stage 2H.7 findings concerning unrelated providers and sensitive-data handling were not changed by this stage.

## Stage 2H.18 — Current feed and destination review

Current `createPhishingDatabaseTool()` has no `feedUrl` parameter and fetches only `DEFAULT_FEED_URL`, after exact HTTPS host/path validation. The active server constructs it without a destination override; the legacy `PHISHING_DATABASE_FEED_URL` setting is not referenced. Fetch uses GET with `redirect: "error"`, a default 10-second abort timeout (the active server permits an operator timeout-duration override), and a 5 MiB streamed byte ceiling before UTF-8 decode and parsing. Non-200 responses, malformed/empty feed data, oversize bodies, timeouts, and network failures become bounded messages; a previously loaded cache can serve stale data, otherwise the tool reports unavailable. No code change was needed for this stage.

Review of server fetch call sites found no fetch destination derived from a user-submitted indicator. Security-tool indicators are sent as path/query/body data to fixed provider hosts; the Observatory request uses a fixed API endpoint and submits only the parsed hostname as data. Other destinations are server-configured AI provider endpoints and the validated `SUPABASE_URL` authentication endpoint, not request URLs. The shared `fetchWithRetry(url)` accepts a URL argument internally, but active security-tool callers construct it from fixed provider hosts. This source review does not establish DNS integrity, network-layer egress controls, proxy behavior, production environment values, or that deployed code matches this worktree. These remain deployment responsibilities; a fixed URL and disabled redirects do not guarantee immunity to DNS compromise, host compromise, proxy manipulation, or other infrastructure-level routing risks.
